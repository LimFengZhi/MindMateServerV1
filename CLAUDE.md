# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Run the dev server (http://localhost:5000)
python run.py                      # env toggles: FLASK_DEBUG=1, FLASK_HOST=0.0.0.0

# Replace the Resources content in Supabase (content lives in this script)
python scripts/scrape_resources.py --dry-run   # preview
python scripts/scrape_resources.py             # full-replace upload
```

- The venv is `.venv/` (Windows: `.venv\Scripts\python.exe`). PyTorch is installed separately and only needed when `AI_MODE=real` (see README).
- There is no test suite or linter configured.
- `GET http://localhost:5000/health` reports which agents are running real models vs stubs — check it after toggling `AI_MODE`.
- **Database DDL cannot be run from code.** The backend talks to Supabase via PostgREST (supabase-py), so any schema change means editing `schema.sql` and pasting it into the Supabase SQL editor manually. ⚠️ `schema.sql` is a **full reset script by design**: every run drops all app tables **and deletes every auth account**, then recreates the schema — never additive migrations. After a reset: boot re-seeds agreement/prompts/self-tests, `scripts/scrape_resources.py` must be rerun, and the first admin must be re-registered + re-promoted (SQL snippet at the bottom of schema.sql; full checklist in README §Resetting the database). Registration requires name + phone + date of birth + gender (all validated in auth/routes.py, all stored on `profiles` via signup metadata + the handle_new_user trigger; users edit them later at `/profile` via `PATCH /auth/me`, which is bounded by `repo.EDITABLE_PROFILE_FIELDS` so role/email can never be self-assigned). **Age is never a column** — `profiles.date_of_birth` is stored and `app/profile_utils.py:age_from_dob` derives the number wherever one is shown (registration validation, /auth/me, the admin users table, the session report), mirrored in JS by `ageFromDOB`/`genderLabel` in common.js.
- Config has two sources, both read ONLY through `app/config.py` (`Config`): `.env` for secrets + machine-specific values (keys, model paths, devices — template: `.env.example`) and `config.yaml` at the project root for committed app tuning (chatbot generation params, summarizer tokens, `memory.recent_turns`, `profile.min_age`/`max_age`, risk thresholds, the crisis message). Never scatter `os.getenv` or yaml loads elsewhere; missing YAML keys fall back to defaults in config.py.

**Before touching admin features, read `CODING_GUIDE.md`** — it defines the user-side / admin-side split: admin work stays in `app/admin/`, `app/db/admin_repo.py`, `templates/admin/`, `static/js/admin/`, `static/css/admin.css` (+ guard/blueprint registration), and must not modify user-side routes, `repo.py`, the AI pipeline, or the published API shapes in `API.md`.

## Architecture

Flask app factory (`app/__init__.py:create_app`) + blueprints: `auth` (/auth), `chat` (/chat), `sessions` (/sessions), `resources` (/api/resources), `self_test` (/api/tests), `agreements` (/agreements), `admin`/`admin_api` (/admin + /admin/testing/multi-agent + /api/admin — role-guarded per request: `staff_required` allows staff+admin, `admin_required` allows only admin, who creates staff accounts by email via Supabase's auth admin API in `app/admin/service.py`; admin queries live in `app/db/admin_repo.py`, never in repo.py — except the id-scoped `get_profile`/`set_message_feedback` helpers admin routes may reuse; staff enter via the login page's "Login as staff" link → /admin/login; the first admin is promoted via SQL). The staff backoffice (vertical sidebar nav in `templates/admin/dashboard.html`): dashboard views (Dashboard — stat cards + 14-day chatbot-usage/escalation bar charts from `GET /api/admin/activity`; Suicide Alert — `GET /api/admin/alerts/suicide?period=today|week|month`, escalations in the window + affected users ranked highest-first with their Suicide Risk Check uptake in that same window (`admin_repo.get_suicide_alerts`, period math: 'today' = UTC midnight, week/month = rolling 7/30 days); all-user emotion analysis, User Sessions — level 1 is ALL registered users with profile info from `GET /api/admin/users` (`list_users_overview`, includes sessionless users) → user→chat→transcript review with per-reply rating/feedback via the messages feedback columns, JSON export, plus a per-user 📄 session-analysis report: `POST /api/admin/users/<id>/report` (rate-limited 6/min) runs `app/agents/report.py:build_session_report` — the pipeline's summarizer weights via a second `LocalChatModel` with `report.max_new_tokens` from config.yaml, guided by the admin-editable `session_analysis` DB prompt, stub fallback when models are off — over the `report.recent_sessions` most recent chats, cached in-memory in routes so `GET /api/admin/users/<id>/report.pdf` (fpdf2, `app/admin/pdf_report.py`, latin-1-sanitized) downloads without regenerating (404 until Generate is clicked; cache clears on restart)), content editors (an 'Editing' tab grouping Resources / Prompts / Agreements as sub-tabs — CRUD for resources / prompts, agreement edit, the merged Test Analysis view — self-test analytics + per-attempt Individual Logs via `GET /api/admin/analytics/tests/<id>/attempts` + the self-tests CRUD editor in one tab — and a paged read-only viewer over the local training datasets in `app/resources/datasets/*.json` via `GET /api/admin/dataset/<chatbot|classifier>`) — editor writes return a bool from `admin_repo._attempt`, mapped to `{ok}`/500 by `_write_response` in routes — plus the Test Chat tab: 'Normal — chat as a user' links to the multi-agent test bench page (real sessions on the staff member's own account, messages-feedback columns), and two comparison modes run via `POST /api/admin/bench/run` ('single_vs_multi' = the SAME app-model weights AND same rules — the 'single' DB prompt is the composed prompt minus its summary/memory parts — alone vs full pipeline; 'models3' = Gemma/Llama3.2/Qwen3, the two extras LAZY-loaded by `registry.load_bench_model` on first use, never at boot; logic in `app/agents/bench.py`). Comparison runs live in `bench_session` rows (renamable/deletable comparison chats, staff-scoped, lazy-created on first run and auto-titled) — each variant continues ITS OWN history across a session's turns (`get_bench_histories`); variants persist to `bench_result` (one row per variant, run_id groups a turn, session_id links the chat) with rating/feedback via `POST /api/admin/bench/<id>/feedback`. Missing tables degrade gracefully (sessionless one-shot runs) with a hint to re-run schema.sql, which contains all bench tables. Staff pages load `static/js/admin/review_helpers.js` (role guard + shared feedback/export helpers) before their page script. Pages are Jinja templates (`templates/base.html` → `app_base.html` → per-page; shared sidebar in `templates/partials/sidebar.html`, parameterized by `{% set active_page %}`) with vanilla JS in `app/static/js/` — `common.js` holds the `api()` fetch wrapper, auth/localStorage helpers, and `escapeHTML`, used by every page.

**Ownership is enforced in Python, not by the database.** The backend uses the Supabase *service* key, which bypasses RLS (the RLS policies in schema.sql are defense-in-depth only). Every user-scoped query in `app/db/repo.py` (the single data-access layer — all Supabase reads/writes live there) filters by `user_id`, and the route guards in `app/auth/decorators.py` do the checks: `login_required` validates the JWT into `g.user`; `session_required` additionally verifies the URL's `<session_id>` belongs to the caller (`g.session`). Error responses always go through `app/http_utils.json_error` so the frontend gets uniform `{error}` JSON; the global handler in `create_app` maps transient httpx connection failures (dropped Supabase pooled connections) to a retryable 503, and `admin_repo._retry_once` gives poll-heavy admin reads one immediate retry on a fresh connection (never for `APIError` — real Postgres errors must surface).

**Multi-agent chat pipeline** (`app/agents/` — LangChain provides the components, LangGraph the control flow; one `graph.invoke` per turn via `answer()` in `app/agents/graph.py`, the only entry point routes use):
`load_context → diagnose → (conditional route_turn) → crisis_reply | summarize → generate → persist`. Layers, by dependency direction: `state.py` (ChatState TypedDict) · `guards.py` (pure regex/rule helpers — no ML imports, safe to import from repo.py) · `stubs.py` (rule-based fallbacks, same input dicts as the chains they back) · `chat_models.py` (ONE generic `LocalChatModel(BaseChatModel)` wrapping any registry (tokenizer, model) pair; prompt formatting is the tokenizer's own `apply_chat_template`, `fold_system=True` for Gemma's no-system-role template, stop tokens derived from the tokenizer; raises `ModelUnavailable` when weights aren't loaded) · `prompts.py` (ChatPromptTemplates — the admin-edited DB text enters as a **value** `{system_text}`, never as a template, so literal braces can't break formatting) · `chains.py` (the composition: `reply_chain = prompt | chatbot | TidyReplyParser` with `.with_retry` resampling case-note replies once, `.with_fallbacks` → fixed warm fallback for repeated case notes, outermost `.with_fallbacks` → stub; `summarize_chain`, `diagnose_chain` similarly; **swapping the chatbot model = two .env lines**: `CHAT_MODEL_PATH` + `CHAT_MODEL_FAMILY` (gemma2|qwen3|llama32) — `CHAT_FAMILIES` in chains.py maps the family to fold_system/stop-token/system-prefix details, incl. Qwen3's `/no_think` non-thinking control; chains are reusable stand-alone — `reply_chain.batch()` works in evaluation notebooks) · `nodes.py` (thin state→partial-state functions; `RECENT_TURNS` lives here — hybrid memory: the last `memory.recent_turns` (2) exchanges verbatim, older turns only through the summary; validated by the single-vs-multi CEHS evaluation) · `graph.py` (wiring + compiled singleton; `build_chat_graph()` returns the uncompiled graph) · `voice.py` (faster-whisper, outside the graph) · `registry.py` (model loading + readiness flags for /health) · `prompt_loader.py` + `prompt/` (DB-backed system-prompt text, .txt seed/fallback). The persist node stores the turn to `messages` with emotion/escalation metadata (feeding the analysis page) and raises `SessionDeleted` → routes map to 404 if the chat was deleted mid-generation. There is NO greeting shortcut: bare greetings go through the normal pipeline, and the welcome words are purely a frontend empty-state bubble in chat.html/chat.js (`.welcome-msg`, never persisted). Guardrails for the fine-tune's habits: `tidy_reply`/case-notes detection in `guards.py` (NOTE: the fine-tune imitates MentalChat16K's long advice-heavy answers and often ignores the composed prompt's '2-4 sentences'/no-advice rules — the base instruct model follows them, measured ~5.7 vs 3.0 sentences avg; no length enforcement is applied by design) (strips `[Name]`-style tokens and `rawDesc` artifacts leaked from MentalChat16K, trims the half-sentence left by the token cap; third-person "The patient describes…" replies are rejected by `TidyReplyParser`). Deliberately NOT used (document, don't "fix"): LangGraph checkpointer memory (history lives in Supabase across processes; the hybrid verbatim-window + summary memory is a research design choice) and `interrupt` for experiment mode (counsellor approval spans processes, so DB status + polling is the correct mechanism).

**Experiment mode (supervised counselling):** sessions carry `mode` ('multi' | 'experiment'). In experiment sessions `answer()` stores the pipeline output as a PENDING draft (`messages.status='pending'`, `draft_reply` set, `reply` null — crisis replies included, by design) and returns only `{messageID, status:"pending"}`. Staff resolve drafts ONLY on the Live Counselling page (`/admin/live`, `live.js`): a counsellor takes charge of up to 2 USERS at a time, then picks one of each user's experiment sessions to watch (`GET /api/admin/live-sessions` grouped client-side by email; transcripts via the polled `GET /api/admin/sessions/<id>`; staff rename via `POST /api/admin/sessions/<id>/rename`; users are exclusively claimed per staff member via `POST /api/admin/live-claim`/`live-release` — in-memory registry in `app/admin/live_claims.py`, kept alive by the poll heartbeat, ~15s TTL, single-process only) and approves/edits pending drafts inline via `POST /api/admin/review/<id>` (race-guarded by a conditional update on `status='pending'` → 409): approve → `status='approved'`, `reply=draft_reply`; edit → `status='rejected'`, `reply=` staff text, draft preserved. The user chat polls `GET /sessions/<id>/pending` (~3 s) until delivery. **Draft-privacy rule:** user-facing endpoints never expose `draft_reply` or the approved/rejected distinction — they map status to `pending`/`delivered` only. Polling endpoints need their own `@limiter.limit` (the 300/hour default would kill a poll loop).

Two safety layers run regardless of AI mode: the lexical crisis regex in `app/agents/guards.py` (`crisis_keywords_present`) escalates even when the ML classifier misses, and the PHQ-9 self-harm item in the self-tests always attaches crisis contacts to the result. A third layer suggests the **Suicide Risk Check** quiz: `needs_risk_check` in `guards.py` (escalated turns only) adds `suggestedTest: "suicide-risk-check"` to the reply payload — attached identically to live replies (the graph's persist node), transcripts, and delivered experiment turns (`repo._reply_extras`); the chat renders it as a link to `/resources#test=suicide-risk-check`, which the Resources page auto-opens. A fourth, opt-in layer emails the counselling information to the user on every escalated turn: `notify_crisis` in `app/email_utils.py`, called from the persist node (experiment mode included), fire-and-forget on a daemon thread, toggled by `crisis_email.enabled` in `config.yaml` (subject/intro/cooldown in the same block) with the SMTP credentials in `.env` (in-memory per-user cooldown, default 60 min, single-process like live_claims; the body reuses `crisis_message` so helplines never drift).

**Stub/real AI duality:** with `AI_MODE=stub` (default) every chain falls through to its rule-based stub and the app boots instantly; with `real`, `app/agents/registry.py` loads local models (heavy imports happen inside loaders; torch imports stay inside `LocalChatModel._generate` and `_diagnose_real`). The fallback is LangChain-native: every chain's outermost policy is `.with_fallbacks([RunnableLambda(stub)])` — the real path raises `ModelUnavailable` when `registry.*_ready` is false and logs any inference-time failure before the stub takes over, so a model failing at load *or* inference never breaks a chat turn. Stubs take the SAME input dicts as the chains they back (documented in `chains.py`) — keep that contract when changing either side. Voice (faster-whisper) is independent of `AI_MODE` and is preloaded at boot by `registry.load_all()` in BOTH modes (it has no stub to fall back on, so a cold first transcription would otherwise stall the request); `voice.py` still calls `load_voice()` per request, which is then a no-op and covers `create_app(load_models=False)`.

**Agent prompts live in the DB** (`prompts` table, edited via the admin dashboard's Prompts editor or the Supabase dashboard, ~15 s cache in `app/agents/prompt_loader.py`), with the bundled `.txt` files in `app/agents/prompt/` as seed + fallback — this is the designed integration point; admin features never modify prompt-loader code. Rows are identified by the `key` column ('composed', 'summarise') everywhere — the loader, seeder, and the admin editor (which labels it "name" in the UI but reads/writes `key`).

**Content ownership split:**
- *Resources* (in-app guides/exercises with an Info tab, steps tab, and reference link) are owned by `scripts/scrape_resources.py` — it full-replaces the `resources` table; they are **not** seeded on boot. ⚠️ The admin dashboard now also has a resources CRUD editor writing to the same table: re-running the script **wipes admin edits**, so confirm with the user before running it.
- *Self-tests* (PSS-10 stress, Rosenberg self-esteem, PHQ-9 depression, Suicide Risk Check adapted from the SWSPHN screening tool) live in `app/resources/self_test/`: `definitions.py` is seeded into the `test` table on boot; `routes.py` scores submissions **server-side** (each option carries its value, so reverse-scored items need no special casing; the SWSPHN "immediate plan" option carries value 10 so it always lands in the Emergency band) and records attempts in `test_created`. `alert_always: true` in a test's scoring makes the crisis-contacts alert unconditional — the client renders any alert ABOVE the score.
- Boot seeding (`app/db/seed.py`): the agreement inserts only when its table is empty; prompts AND self-tests TOP UP — any prompt key / definitions.py slug missing from its table is inserted (existing rows never touched), so new prompts (e.g. `session_analysis`) and instruments reach existing databases without a reset.

**Offline ML work (not part of the Flask app):** the weights loaded when `AI_MODE=real` live under `models/chat_models/` and `models/classifier_models/` (defaults in `Config`, overridable via `CHAT_MODEL_PATH`/`CLASSIFIER_PATH`), but `models/` is **gitignored** — a fresh clone has no weights and every agent falls back to its stub until they're supplied. `scripts/download_models.py` fetches them from Hugging Face (`Fz0212/mindmate-*` + the int8 ONNX classifier; idempotent, also the Docker entrypoint's first step — `Dockerfile`/`docker-compose.yml` deploy on a GPU host with one gunicorn worker, weights in a volume, secrets via env_file). The classifier loader auto-detects a `*.onnx` file in `CLASSIFIER_PATH` and loads it through optimum-onnxruntime; both the fp32 RoBERTa and the int8 export mislabel some explicit self-harm phrasings (e.g. "I want to kill myself" → Personality disorder) — the lexical crisis regex (safety layer 1) is what catches those, by design. `fine_tuning_chatbot/` is the fine-tuning research pipeline, **gitignored like its data in `/data/`** (local-only; a fresh clone has neither): a QLoRA study (3 models × 1 dataset — MentalChat16K; amod was removed; Shadow-FT was dropped — `methods: [qlora]`, the `base_id` entries are reference only) organised as `fine_tuning_chatbot/{training,evaluate,eda}/` with the shared `config.yaml` + `ft_utils.py` at the package root (each subfolder's scripts/notebooks add the parent to sys.path). Training is REPLY-ONLY (`completion_only_loss`, prompt/completion columns from `ft_utils.get_formatted`, NO system prompt in training — the deployment prompt arrives as a novel instruction at inference) via the reusable `trainer.train(model_key)` in `training/trainer.py`; the thin `training/train_*.ipynb` notebooks just call it, then `training/merge_models.ipynb` and the unified evaluation (`evaluate/evaluator.py` stores one generation pass per system on the test split; `evaluate/evaluate_metric.ipynb` scores it, `evaluate/evaluate_llm_judge.ipynb` judges a seeded sample of the same files via `llm_judge.py`, and `evaluate/evaluate_single_vs_multi.ipynb` compares the app's single-agent vs multi-agent architecture on MULTI-TURN data — `single_vs_multi.n_cases` (10) seeded conversations from `Jingy2000/multi-turn-counsel-chat` (CounselChat Q&A expanded to dialogues with GPT-4; cached at data_root/raw/multiturn_counselchat.json, leading counselor greeting dropped), replayed TEACHER-FORCED up to `max_client_turns` (6) client turns: single = 'single' prompt + verbatim history, multi = RoBERTa diagnosis + crisis routing + the APP's summarizer model writing `{summarised_history}` (summary-only memory, like deployment; summarizer id read from the app .env), the `single_vs_multi.model_key` tuned model in both arms (family-correct chat template, byte-matched against the tokenizer's own), stored to `results/generations/pipeline_<single|multi>.jsonl`; replies are scored per turn on the SoulChat CEHS rubric (Table 2 of arXiv:2311.00273 — content/empathy/helpfulness 0-2, safety 0-1, prompt in `evaluate/cehs_prompt.txt`) by the same GLM judge, resume-safe to `results/single_vs_multi/cehs_raw.jsonl`; `evaluate/single_vs_multi.py` reads prompts/thresholds/crisis message+regex FROM the app (prompt .txt files, root config.yaml + .env, guards.py by file path) so it can't drift from deployment; `eda/eda_eval_dataset.ipynb` documents both evaluation data sources and the lineage vs the prior mhsupportchat study, whose `data/test.csv` was a row-level split of the same ShenLab/MentalChat16K corpus — 1,040 of its test questions sit in THIS study's train split, so cross-study scores are not comparable), and tuned models land in `models/chat_models/<dataset>/<model>[_merged]/` (`models_root` in config.yaml), alongside the app-served weights. The app's training data in `app/resources/datasets/` (large JSON — don't read whole files) is browsable read-only in the admin dashboard.

**Frontend conventions:** strict CSP (set in `create_app`) — no external scripts/frames; inline `onclick` handlers are why `'unsafe-inline'` is allowed, and all dynamic content must pass through `escapeHTML`. Card clicks pass array indexes, not interpolated ids. `api()` auto-redirects to /login on 401 **except** for `/auth/*` paths (a failed login is also a 401). The `sidebar-open` class on `<html>` drives the sidebar on both desktop and mobile; its no-flash default is set by an inline script in `app_base.html`'s head. **Responsive rules (user side, `style.css`):** breakpoints are 901+ / ≤900 (off-canvas drawer + scrim) / ≤760 / ≤380, plus a `(hover: none) and (pointer: coarse)` block that sizes controls to `--tap` (44px) and inputs to 16px — keyed on the POINTER, not width, so a tablet gets touch sizing and a narrow desktop window doesn't. **Every breakpoint lives at the END of the file**: a page section appended after them silently out-ranks its own overrides (same specificity, later wins). `viewport-fit=cover` is set on `app_base.html` + `login.html`, so anything on a physical edge (`.topbar`, `#composer`, `.content`, `.auth-wrap`, the fixed `#sidebar`) pads itself with the `--sa-top/right/bottom/left` vars wrapping `env(safe-area-inset-*)` — and any `padding` shorthand in a media query must re-state them or it resets the base value. Heights use `100vh` then `100dvh` so the mobile URL bar can't clip the layout.
