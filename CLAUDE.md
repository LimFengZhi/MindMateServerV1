# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Run the dev server (http://localhost:5000)
python run.py                      # env toggles: FLASK_DEBUG=1, FLASK_HOST=0.0.0.0

# Replace the Resources content in Supabase (content lives in this script)
python scripts/scrape_resources.py --dry-run   # preview
python scripts/scrape_resources.py             # full-replace upload
```

- The venv is `.venv/` (Windows: `.venv\Scripts\python.exe`). PyTorch is installed separately and only needed when `AI_MODE=real` (see README).
- There is no test suite or linter configured.
- `GET http://localhost:5000/health` reports which agents are running real models vs stubs — check it after toggling `AI_MODE`.
- **Database DDL cannot be run from code.** The backend talks to Supabase via PostgREST (supabase-py), so any schema change means editing `schema.sql` and pasting it into the Supabase SQL editor manually. ⚠️ `schema.sql` is a **full reset script by design**: every run drops all app tables **and deletes every auth account**, then recreates the schema — never additive migrations. After a reset: boot re-seeds agreement/prompts/self-tests, `scripts/scrape_resources.py` must be rerun, and the first admin must be re-registered + re-promoted (SQL snippet at the bottom of schema.sql).
- Config comes only from `.env` at the project root (template: `.env.example`), read through `app/config.py` (`Config`). Never scatter `os.getenv` elsewhere.

**Before touching admin features, read `CODING_GUIDE.md`** — it defines the user-side / admin-side split: admin work stays in `app/admin/`, `app/db/admin_repo.py`, `templates/admin/`, `static/js/admin/`, `static/css/admin.css` (+ guard/blueprint registration), and must not modify user-side routes, `repo.py`, the AI pipeline, or the published API shapes in `API.md`.

## Architecture

Flask app factory (`app/__init__.py:create_app`) + blueprints: `auth` (/auth), `chat` (/chat), `sessions` (/sessions), `resources` (/api/resources), `self_test` (/api/tests), `agreements` (/agreements), `admin`/`admin_api` (/admin + /admin/testing/multi-agent + /api/admin — role-guarded per request: `staff_required` allows staff+admin, `admin_required` allows only admin, who creates staff accounts by email via Supabase's auth admin API in `app/admin/service.py`; admin queries live in `app/db/admin_repo.py`, never in repo.py — except the id-scoped `get_profile`/`set_message_feedback` helpers admin routes may reuse; staff enter via the login page's "Login as staff" link → /admin/login; the first admin is promoted via SQL). The staff backoffice: dashboard views (overview, all-user emotion analysis, user→chat→transcript review with per-reply rating/feedback via the messages feedback columns, JSON export), content editors (CRUD for resources / prompts / self-tests, agreement edit, self-test analytics, and a paged read-only viewer over the local training datasets in `app/resources/datasets/*.json` via `GET /api/admin/dataset/<chatbot|classifier>`) — editor writes return a bool from `admin_repo._attempt`, mapped to `{ok}`/500 by `_write_response` in routes — plus the multi-agent test bench, whose chats are real sessions on the staff member's own account. Staff pages load `static/js/admin/review_helpers.js` (role guard + shared feedback/export helpers) before their page script. Pages are Jinja templates (`templates/base.html` → `app_base.html` → per-page; shared sidebar in `templates/partials/sidebar.html`, parameterized by `{% set active_page %}`) with vanilla JS in `app/static/js/` — `common.js` holds the `api()` fetch wrapper, auth/localStorage helpers, and `escapeHTML`, used by every page.

**Ownership is enforced in Python, not by the database.** The backend uses the Supabase *service* key, which bypasses RLS (the RLS policies in schema.sql are defense-in-depth only). Every user-scoped query in `app/db/repo.py` (the single data-access layer — all Supabase reads/writes live there) filters by `user_id`, and the route guards in `app/auth/decorators.py` do the checks: `login_required` validates the JWT into `g.user`; `session_required` additionally verifies the URL's `<session_id>` belongs to the caller (`g.session`). Error responses always go through `app/http_utils.json_error` so the frontend gets uniform `{error}` JSON; the global handler in `create_app` maps transient httpx connection failures (dropped Supabase pooled connections) to a retryable 503, and `admin_repo._retry_once` gives poll-heavy admin reads one immediate retry on a fresh connection (never for `APIError` — real Postgres errors must surface).

**Multi-agent chat pipeline** (`app/chat/orchestrator.py`, one call per turn):
diagnostic agent (emotion + risk) → routing layer 2 (crisis escalation — returns a fixed crisis message and skips generation) → summarize agent (long-term memory; `RECENT_TURNS = 0` means the chatbot sees a summary only, never verbatim history) → prompt builder → chatbot agent. The turn is persisted to `messages` with emotion/escalation metadata, which feeds the per-session analysis page. Two guardrails compensate for the fine-tune's habits: a first-turn bare greeting ("Hi") returns the fixed `WELCOME_MESSAGE` without generating (the tuned model invents a backstory for content-free inputs), and every raw generation passes through `_tidy_reply` in `chatbot_agent.py` (strips `[Name]`-style template tokens leaked from the MentalChat16K data, trims the half-sentence left by the token cap).

**Experiment mode (supervised counselling):** sessions carry `mode` ('multi' | 'experiment'). In experiment sessions `answer()` stores the pipeline output as a PENDING draft (`messages.status='pending'`, `draft_reply` set, `reply` null — crisis replies included, by design) and returns only `{messageID, status:"pending"}`. Staff resolve drafts ONLY on the Live Counselling page (`/admin/live`, `live.js`): a counsellor takes charge of up to 2 USERS at a time, then picks one of each user's experiment sessions to watch (`GET /api/admin/live-sessions` grouped client-side by email; transcripts via the polled `GET /api/admin/sessions/<id>`; staff rename via `POST /api/admin/sessions/<id>/rename`; users are exclusively claimed per staff member via `POST /api/admin/live-claim`/`live-release` — in-memory registry in `app/admin/live_claims.py`, kept alive by the poll heartbeat, ~15s TTL, single-process only) and approves/edits pending drafts inline via `POST /api/admin/review/<id>` (race-guarded by a conditional update on `status='pending'` → 409): approve → `status='approved'`, `reply=draft_reply`; edit → `status='rejected'`, `reply=` staff text, draft preserved. The user chat polls `GET /sessions/<id>/pending` (~3 s) until delivery. **Draft-privacy rule:** user-facing endpoints never expose `draft_reply` or the approved/rejected distinction — they map status to `pending`/`delivered` only. Polling endpoints need their own `@limiter.limit` (the 300/hour default would kill a poll loop).

Two safety layers run regardless of AI mode: the lexical crisis regex in `app/agents/routing.py` (`crisis_keywords_present`) escalates even when the ML classifier misses, and the PHQ-9 self-harm item in the self-tests always attaches crisis contacts to the result. A third, softer layer suggests the **Suicide Risk Check** quiz: `needs_risk_check` in `routing.py` (escalated turn, or 'Suicidal' label ≥ `RISK_QUIZ_THRESHOLD`, default 0.5) adds `suggestedTest: "suicide-risk-check"` to the reply payload — attached identically to live replies (`orchestrator.answer`), transcripts, and delivered experiment turns (`repo._reply_extras`); the chat renders it as a link to `/resources#test=suicide-risk-check`, which the Resources page auto-opens.

**Stub/real AI duality:** with `AI_MODE=stub` (default) every agent runs a rule-based stub and boots instantly; with `real`, `app/ml/registry.py` loads local models (heavy imports happen inside loaders). Agents extend `BaseAgent` and route through `_with_fallback` — a model failing at load *or* inference time falls back to its stub, and the app keeps running. Voice (faster-whisper) is independent of `AI_MODE` and lazily loaded on first use.

**Agent prompts live in the DB** (`prompts` table, edited via the admin dashboard's Prompts editor or the Supabase dashboard, ~15 s cache in `app/prompt_builder/loader.py`), with the bundled `.txt` files as seed + fallback — this is the designed integration point; admin features never modify prompt-builder code. Rows are identified by the `key` column ('composed', 'summarise') everywhere — the loader, seeder, and the admin editor (which labels it "name" in the UI but reads/writes `key`).

**Content ownership split:**
- *Resources* (in-app guides/exercises with an Info tab, steps tab, and reference link) are owned by `scripts/scrape_resources.py` — it full-replaces the `resources` table; they are **not** seeded on boot. ⚠️ The admin dashboard now also has a resources CRUD editor writing to the same table: re-running the script **wipes admin edits**, so confirm with the user before running it.
- *Self-tests* (PSS-10 stress, Rosenberg self-esteem, PHQ-9 depression, Suicide Risk Check adapted from the SWSPHN screening tool) live in `app/resources/self_test/`: `definitions.py` is seeded into the `test` table on boot; `routes.py` scores submissions **server-side** (each option carries its value, so reverse-scored items need no special casing; the SWSPHN "immediate plan" option carries value 10 so it always lands in the Emergency band) and records attempts in `test_created`. `alert_always: true` in a test's scoring makes the crisis-contacts alert unconditional — the client renders any alert ABOVE the score.
- Boot seeding (`app/db/seed.py`): agreement + prompts insert only when their table is empty; self-tests TOP UP — any definitions.py slug missing from the `test` table is inserted (existing rows never touched), so new instruments reach existing databases without a reset.

**Offline ML work (not part of the Flask app):** the weights loaded when `AI_MODE=real` live under `models/chat_models/` and `models/classifier_models/` (defaults in `Config`, overridable via `CHAT_MODEL_PATH`/`CLASSIFIER_PATH`), but `models/` is **gitignored** — a fresh clone has no weights and every agent falls back to its stub until they're supplied out-of-band. `fine_tuning_chatbot/` is the fine-tuning research pipeline, **gitignored like its data in `/data/`** (local-only; a fresh clone has neither): a QLoRA study (3 models × 2 datasets; Shadow-FT was dropped — `methods: [qlora]`, the `base_id` entries are reference only) driven entirely by `fine_tuning_chatbot/config.yaml`, which `ft_utils.py` loads directly; the work runs through the `train_*.ipynb` / `evaluate_*.ipynb` / `merge_models.ipynb` notebooks plus `llm_judge.py`, and tuned models land in `models/chat_models/<dataset>/<model>[_merged]/` (`models_root` in config.yaml), alongside the app-served weights. The app's training data in `app/resources/datasets/` (large JSON — don't read whole files) is browsable read-only in the admin dashboard.

**Frontend conventions:** strict CSP (set in `create_app`) — no external scripts/frames; inline `onclick` handlers are why `'unsafe-inline'` is allowed, and all dynamic content must pass through `escapeHTML`. Card clicks pass array indexes, not interpolated ids. `api()` auto-redirects to /login on 401 **except** for `/auth/*` paths (a failed login is also a 401). The `sidebar-open` class on `<html>` drives the sidebar on both desktop and mobile; its no-flash default is set by an inline script in `app_base.html`'s head.
